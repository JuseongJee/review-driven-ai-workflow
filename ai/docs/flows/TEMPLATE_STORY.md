# 왜 이 템플릿을 만들었는가

이 문서는 이 템플릿을 처음 보는 사람이
"왜 이런 문서가 많지?"
"왜 바로 코드부터 안 만들지?"
"왜 Claude, Codex, 외부 AI 역할을 나눴지?"
같은 질문에 답할 수 있게 만든 설명 문서입니다.

자세한 설계 배경은 `ai/docs/adr/0002-template-context.md`에 있고,
이 문서는 그 내용을 사람 기준으로 풀어 쓴 버전입니다.

## 처음에는 다들 비슷하게 시작한다

AI 코딩을 처음 붙이면 흐름은 대체로 단순하다.

요구사항을 한 줄 적습니다.
AI가 코드를 만듭니다.
고쳐 달라고 몇 번 더 말합니다.
그러다 어느 순간 뭔가 돌아가는 것처럼 보인다.

작은 실험에서는 이 방식이 꽤 잘 먹힌다.
문제는 프로젝트가 조금만 커져도 바로 드러난다.

- 왜 이렇게 구현했는지 기록이 없다
- 변경 영향 분석이 빠진다
- 테스트 전략이 뒤늦게 나온다
- 기존 코드베이스 수정에서는 놓치는 범위가 커진다
- 리뷰가 없어서 AI가 낸 답을 AI가 다시 의심하지 않는다

결국 "AI가 빨라졌다"가 아니라
"AI가 빨리 이상한 방향으로 달린다"가 되기 쉽다.

이 템플릿은 그 지점에서 출발했다.
코드를 더 빨리 찍는 템플릿이 아니라,
AI가 성급하게 구현부터 하지 못하게 막는 템플릿이 필요했다.

## 그래서 먼저 순서를 바꿨다

핵심 생각은 단순하다.

코드는 마지막에 나온다.
먼저 나와야 하는 것은 다음이다.

REQUEST
-> SPEC
-> PLAN
-> IMPLEMENT
-> VERIFY
-> REVIEW

즉, 이 템플릿은 "AI에게 더 잘 시키는 법"보다
"AI가 어떤 순서로 일하게 할 것인가"를 먼저 정합니다.

이 구조를 넣은 이유는 명확하다.

- REQUEST는 요구사항을 흐리지 않게 만든다
- SPEC은 무엇을 바꿀지 경계를 만든다
- PLAN은 어떻게 바꿀지 실행 순서를 만든다
- VERIFY는 구현 이후 품질 확인을 강제한다
- REVIEW는 Builder가 놓친 부분을 다시 잡게 만든다

이렇게 하면 큰 작업일수록 산출물이 남고,
나중에 사람이 읽어도 맥락을 복원할 수 있다.

## 그런데 Claude 하나만으로는 충분하지 않았다

Claude는 설계하고, 만들고, 정리하는 데 강하다.
그래서 이 템플릿의 중심은 지금도 Claude다.

문제는 Builder 하나만 있으면 속도는 빨라도 견제가 약하다는 점이다.

그래서 역할을 나눴다.

- Claude는 Builder
- Codex는 Critic
- 외부 AI(예: Gemini)는 Compressor

이 역할 분리는 도구 취향의 문제가 아니라 작업 분업의 문제다.

### Claude가 Builder인 이유

Claude는 요구사항을 정리하고,
설계를 풀고,
코드를 쓰고,
리팩터링하고,
테스트까지 이어가는 흐름이 자연스럽다.

그래서 전체 작업을 끌고 가는 주체로 두었다.

### Codex가 Critic인 이유

Codex는 "이 설계에 구멍이 없는가",
"이 diff에 회귀 위험이 없는가",
"이 변경이 너무 복잡하지 않은가"를 묻는 역할에 잘 맞는다.

중요한 건 Codex가 구현 주체가 아니라 검토 주체라는 점이다.
이 템플릿에서는 Builder와 Critic을 의도적으로 분리했다.

### 외부 AI(예: Gemini)가 Compressor인 이유

PRD, API 문서, 로그처럼 길고 거친 입력은 그대로 Builder에게 던지면 집중력이 분산된다.
그래서 먼저 압축하고 요약하는 역할을 따로 뒀다.

이렇게 하면 Claude는 덜 지저분한 입력으로 더 중요한 판단에 집중할 수 있다.

현재 이 역할은 Codex처럼 자동화된 파이프라인이 아니라, 사용자가 필요할 때 외부에서 직접 사용하는 구조다. 가이드는 `ai/docs/library/외부_AI_아이데이션_핸드오프.md`에 있다.

## Superpowers는 뼈대를 주고, 이 템플릿은 운영 규칙을 더했다

Superpowers의 장점은 설계 -> 계획 -> 구현 순서를 자연스럽게 강제한다는 점이다.

특히 다음 흐름이 유용했다.

brainstorming
-> writing-plans
-> implementation

하지만 실제 작업에서는 그것만으로 충분하지 않았다.

- 요청 자체가 덜 구조화될 수 있다
- 리뷰 역할이 분리되지 않는다
- 여러 AI를 섞어 쓰는 운영 규칙이 없다
- 문서와 산출물 위치가 프로젝트마다 흔들릴 수 있다

그래서 이 템플릿은 Superpowers를 대체하려는 것이 아니라,
Superpowers가 들어간 Claude 중심 개발을 더 안정적으로 운영하기 위한 바깥 프레임으로 만들어졌다.

## 그래서 문서 구조도 일부러 단순하게 나눴다

처음 보는 사람이 가장 많이 헷갈리는 부분이 "문서가 왜 이렇게 나뉘어 있지?"다.

의도는 단순하다.

프로젝트 루트에는 핵심 운영 문서만 둡니다.

- `CLAUDE.md`
- `REQUEST.md`
- `PROJECT_CONTEXT.md`
- `CURRENT_TASK.md`
- `WORKING_WITH_AI.md`

이렇게 한 이유는 세 가지다.

- Claude가 바로 참고해야 하는 핵심 문서가 눈에 잘 띄어야 한다
- 작업 문서와 운영 문서를 섞지 않아야 한다
- 지금 작업 상태와 일상 운영 기준을 루트에서 바로 확인할 수 있어야 한다

반대로 `ai/` 아래에는 운영 문서와 도구를 모은다.

- `prompts`: 입력창에 넣는 예문 / 보정 / 수동 복구 프롬프트
- `review_prompts`: 검토 기준
- `flows`: 전체 흐름 설명
- `templates`: 반복 양식
- `adr`: 왜 이런 결정을 했는지 기록
- `superpowers`: spec / plan 산출물 위치

즉, 루트는 "핵심 운영 문서",
`ai/`는 "운영 체계"다.

## spec과 plan을 남기는 이유도 같다

이 템플릿은 큰 작업에서 바로 구현하지 않는다.

새 기능이면 base spec,
기존 코드 변경이면 change spec,
그리고 그 위에 implementation plan을 둡니다.

이렇게 나눈 이유는 실제로 묻는 질문이 다르기 때문이다.

- spec은 "무엇을 바꾸는가"
- plan은 "어떤 순서로 바꿀 것인가"

둘을 합쳐 버리면 설계와 실행이 섞이기 쉽다.
그 결과 검토 포인트도 흐려진다.

반대로 분리해 두면 Codex가 spec / plan을 독립적으로 검토할 수 있고,
구현 전에 위험을 드러내기가 훨씬 쉬워진다.

## 리뷰 파이프라인이 파일 기반인 이유

처음에는 "필요할 때마다 사람이 Claude와 Codex 사이에서 프롬프트를 옮기면 되지 않나?"처럼 보인다.
실제로 초반에는 다들 그렇게 합니다.

그런데 곧 문제가 생긴다.

- 누가 마지막에 무슨 판단을 했는지 남지 않는다
- 긴 검토에서 맥락이 잘린다
- 같은 쟁점을 반복한다
- 사람이 중간 전달자가 되느라 피곤해진다

그래서 `handoffs/review_pipeline/` 세션 구조를 만들었다.

이 파이프라인은 파일을 중심으로 돌아간다.

- `SESSION.md`: 현재 상태와 차례
- `CHECKPOINT.md`: 합의와 쟁점
- `USER_ACTION.md`: 사람에게 물을 질문
- `turns/*.md`: Claude와 Codex의 개별 판단 기록

이 구조의 장점은 분명하다.

- 대화가 아니라 검토 기록이 남는다
- 중간에 멈췄다가 다시 이어갈 수 있다
- 특정 AI에 덜 묶인다
- 나중에 Codex 말고 다른 도구를 붙이기도 쉽다

그리고 지금은 사람이 Codex를 직접 부르지 않아도 된다.
Claude가 세션을 준비하고,
자기 턴을 쓰고,
필요할 때 `run_review_turn.sh`로 Codex를 호출합니다.

사람은 검토 시작만 말하고,
마지막에 "여기서 마무리할까?"에 답하면 된다.

## 그래서 지금 뭐가 편해졌는가

이 템플릿이 주는 편의는 "프롬프트가 많다"가 아니다.
"AI가 덜 멋대로 일한다"에 가깝다.

실제로는 다음이 편해진다.

### 1. 시작이 단순해진다

사용자는 자유 텍스트로 요구사항을 말하면 된다.
그 다음 REQUEST, spec, plan, review 흐름은 템플릿이 잡는다.

### 2. 큰 작업에서 길을 잃지 않는다

무엇을 바꾸는지와 어떻게 바꾸는지가 문서로 분리되어 남는다.
중간에 다른 사람이 들어와도 맥락 복원이 쉽다.

### 3. 리뷰가 이벤트가 아니라 단계가 된다

마지막에 한 번 보는 리뷰가 아니라,
REQUEST 검토,
spec / plan 검토,
최종 diff 검토로 게이트가 생긴다.

### 4. Claude 중심이지만 Claude 종속은 줄었다

오케스트레이션은 Claude가 하지만,
검토 세션은 파일 기반이라 다른 도구 adapter를 붙이기 쉽다.

### 5. 사람은 더 중요한 결정만 하면 된다

AI가 초안 작성, 구조화, 구현, 1차 검토를 담당하고,
사람은 우선순위, 승인, 최종 판단에 집중할 수 있다.

## 이 템플릿은 결국 무엇을 하려는가

한 줄로 요약하면 이 템플릿은
"AI를 잘 쓰는 프롬프트 모음"이 아니라
"AI가 제멋대로 일하지 못하게 만드는 작업 운영 체계"다.

즉 목표는 화려한 자동화가 아니다.

- 요구사항을 구조화하고
- 설계와 계획을 남기고
- 구현 전에 검토하고
- 구현 후에도 다시 검토하고
- 마지막 결정은 사람이 하게 만드는 것

이 흐름이 익숙해지면 사용자는 사실 많은 걸 기억할 필요가 없다.

1. `README.md`를 본다
2. `PROJECT_CONTEXT.md`를 만든다
3. `REQUEST.md`를 만든다
4. 작업을 시작한다
5. spec / plan을 만든다
6. Codex 검토를 돌린다
7. 구현한다
8. 검증한다
9. PR을 정리한다
10. 최종 리뷰 후 판단한다

이 템플릿은 바로 그 순서를 흔들리지 않게 유지하려고 만들어졌다.
